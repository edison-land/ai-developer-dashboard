# “总结全部”逐项更新设计

## 目标

用户点击“总结全部”后，不再等待所有项目结束才看到变化。每完成一个项目：

- 当前卡片立即显示新的总结；
- 顶部显示“已完成 X/总数”；
- 同时累计“更新、缓存、失败”；
- 单个项目失败时继续后面的项目。

归档项目仍然排除，项目处理顺序仍与当前项目列表一致，模型最大并发数仍为 1。

## 方案比较

### 方案 A：在现有批量请求中持续回传进度（采用）

后台仍负责按顺序处理所有项目，但每完成一个就立即回传一条结果。页面接收后直接替换对应卡片。

优点：

- 用户几乎立即看到第一张完成的卡片；
- 保持后台统一控制顺序、缓存和失败处理；
- 不需要额外的任务表、轮询接口或数据库迁移。

限制：

- 页面刷新或请求断开后，当前批次不会自动恢复进度界面。

### 方案 B：后台任务加页面轮询

后台先创建任务编号，页面每隔一段时间询问进度。

优点是更容易恢复中断；缺点是接口、状态管理和清理逻辑明显更多，不符合本次小范围改造。

### 方案 C：浏览器逐个调用单项目总结

页面自己循环调用现有单项目接口。

实现最短，但页面关闭就会中断，而且批量顺序和统计责任会从后台分散到前端，因此不采用。

## 数据流

1. 页面发送一次“总结全部”请求。
2. 后台取得所有未归档项目，并按当前顺序逐个处理。
3. 每个项目完成后，后台更新内存中的项目卡片并回传：
   - 项目路径；
   - 本次结果是更新、缓存还是失败；
   - 已完成数量和总数；
   - 当前累计统计；
   - 成功时附带更新后的项目卡片。
4. 页面收到成功结果后，立即替换对应卡片；收到失败结果时只更新进度和失败数。
5. 全部结束后，后台统一重新采集一次项目状态并回传最终统计。
6. 页面最后统一校准项目、动态和健康状态。

## 页面表现

- 按钮执行中显示“已完成 X/总数”。
- 按钮下方持续显示“更新 X · 缓存 Y · 失败 Z”。
- 当前刚完成的卡片直接更新，不增加全页闪烁或骨架屏。
- 暖白和深墨主题沿用现有状态色，不新增醒目的进度条。
- 完成后恢复“总结全部”，并保留最终统计。

## 错误处理

- 单项目模型错误：记录失败并继续。
- 请求本身断开或数据格式错误：停止页面进度并显示“总结全部失败”。
- 最终重新采集失败：请求失败，但已经成功生成并保存的单项目总结不会丢失。

## 验收边界

自动测试只通过公开接口验证：

1. `POST /api/synthesize-all` 在第一个项目完成后、第二个项目尚未完成时，就能读到第一条进度。
2. 事件顺序与项目顺序一致，最大并发数为 1。
3. 归档项目被排除，旧项目被包含，失败不会中断。
4. 最终统计与逐项事件一致。

浏览器验收验证：

1. 执行状态能显示“已完成 X/总数”。
2. 收到一条模拟进度后，只替换对应卡片。
3. 不在视觉验收中调用真实模型。
