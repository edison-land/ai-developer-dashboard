# v2.0.0 需求：项目任务卡驱动对话执行

> 状态：💡 远期规划，尚未排期
> 灵感来源：2026-07-29 产品讨论
> 阶段目标：用户把项目里的任务卡拖到“进行中”或某个已有对话后，系统自动开启或继续对话，并把执行状态同步回任务卡。

## 要解决的问题

当前工作台主要负责“看见项目状态”，还不能直接把灵感变成一次可执行的 Agent 任务。

实际使用中的痛点是：

- 灵感经常一次出现很多条，需要先按项目存下来，而不是立即全部发送；
- 多条灵感可能有先后顺序，也可能是不同分支；
- 用户需要手动找到对应项目或对话、复制内容、发送，再回来修改状态；
- 任务完成后容易忘记更新看板；
- 新开对话会丢失已有讨论背景，继续旧对话又缺少方便的入口。

v2.0.0 要把工作台从“项目状态看板”推进为“任务入口和执行调度面板”。

## 产品定义

### 项目任务卡

- 每个项目拥有自己的“未发送任务”区域。
- 用户可以快速手写一张任务卡，用来记录灵感、问题或下一步。
- 卡片正文就是初始 Prompt，可以在发送前继续编辑。
- 多张卡片可以先保存、排序和删除，不会在创建时自动发送。
- 任务卡是项目内部的执行单元，不等同于现有的项目阶段卡。

### 自动开启新对话

这是 v2.0.0 的明确版本边界，不提前归入 v1.0.0。

- 用户把任务卡拖到“进行中”，视为明确的启动指令。
- 系统为该项目创建一次新对话或新任务，并自动注入 Prompt。
- 启动成功后，任务卡进入“执行中”，并记录对应的对话或任务标识。
- 同一张卡片不能因为重试、刷新或重复事件而启动多次。
- 如果运行环境会自动创建 worktree，页面需要显示 worktree 信息和对应任务，不能静默创建后让用户无法定位。

### 继续已有对话

- 项目中可以展示可继续的已有对话。
- 用户把任务卡拖到某个对话上，系统把内容发送到该对话，而不是另开新对话。
- 发送前需要明确显示目标项目和目标对话，避免把任务发错上下文。
- 卡片需要保留“发送到了哪个对话”的可追踪记录。
- 如果平台不支持恢复或注入已有对话，必须明确提示，不伪装成已经发送。

### Prompt 与项目上下文

默认 Prompt 由以下内容组成：

1. 用户手写的任务卡正文；
2. 项目当前情况；
3. 项目下一步；
4. 项目路径或仓库定位信息；
5. 用户补充的临时说明。

Agent 负责进入项目后读取仓库、文档和当前代码，不要求用户把完整仓库背景复制到卡片里。

发送前应允许用户预览和修改最终 Prompt。系统不得自动附带密钥、隐私数据或与任务无关的历史内容。

### 执行状态回写

- 对话启动后，任务卡自动进入“执行中”。
- Agent 等待用户输入时，卡片显示“需要处理”。
- 执行失败或连接中断时，卡片显示“失败”，并允许安全重试。
- Agent 完成一次执行后，卡片进入“待验证”，不直接判定业务任务已经完成。
- 用户确认结果后，才把任务卡标记为“完成”。
- 任务卡状态可以向用户提示项目阶段变化，但不能静默覆盖 v0.4.0 已有的人工项目阶段。

### 排队与分支

- 同一项目可以积累多张未发送卡片。
- 用户可以决定发送顺序，不要求灵感按创建顺序立即执行。
- 每张卡片可以选择“开启新对话”或“继续已有对话”。
- 不同方向的卡片可以分别进入不同对话，避免在一个线程里聊岔。
- 本版本不承诺自动判断依赖关系，也不自动并行发送全部卡片。

### 轻量降级方案

如果目标工具暂时不能通过 CLI 或接口自动开启、恢复对话，仍提供可用的基本闭环：

1. 按项目保存未发送消息；
2. 一键复制完整 Prompt；
3. 用户手动发送到目标工具；
4. 一键把卡片标记为已发送或划掉；
5. 保留目标对话备注，方便后续查找。

降级方案用于保持可用性和验证需求，不能对用户显示“已自动发送”。

## 集成方向

优先调查可验证、可维护的接口：

- CLI 或 headless 模式能否创建新对话；
- 能否恢复指定对话并注入 Prompt；
- 能否获得运行中、等待输入、完成和失败状态；
- 新任务与 worktree 的创建、定位和清理方式；
- Codex、Claude Code 或其他 Agent 工具需要哪些权限。

“GUI 负责交互、CLI 负责命令注入”是当前架构假设，不是已经确认的实现方案。

接入 Pi、Oh My Pi 或其他 Agent 运行时可以作为调研选项，但 v2.0.0 不以某个第三方工具为固定前提。

## 验收标准

1. 用户能在指定项目下创建、编辑、排序和删除未发送任务卡。
2. 把卡片拖到“进行中”后，只创建一次新任务，并成功发送可预览的 Prompt。
3. 把卡片拖到已有对话后，内容进入指定对话，不额外创建新对话。
4. 最终 Prompt 至少包含卡片正文、项目当前情况、下一步和项目定位信息。
5. 页面能区分未发送、发送中、执行中、需要处理、待验证、完成和失败。
6. 执行结束后任务卡自动进入“待验证”，用户确认后才进入“完成”。
7. 失败重试不会产生重复对话或重复消息。
8. 自动集成不可用时，一键复制和手动标记已发送仍能完成基本流程。
9. 新对话、已有对话和 worktree 之间的对应关系可以追踪。
10. 自动化操作有测试，并完成至少一种真实 Agent 工具的端到端验证。

## 实施前必须确认

- 首个支持的 Agent 工具和最小接口能力；
- 新建对话、继续对话和读取状态是否有稳定入口；
- worktree 是默认创建、按需创建还是完全交给目标工具；
- 项目、任务卡、对话和 worktree 的身份映射；
- 断线、取消、重试和重复发送的处理规则；
- Prompt 预览、权限和隐私边界；
- v2.0.0 是否依赖 v1.0.0 桌面壳，还是继续采用本地网页加 CLI。

## 本版本不做

- 自研完整 Agent 运行时；
- 自动合并两个对话的上下文；
- 像 Git 一样自动合并对话分支；
- 用接管鼠标键盘作为主要集成方案；
- 无人确认地批量执行所有灵感卡片；
- Agent 停止后直接把业务任务判定为完成；
- 一开始就建设通用 Coding Platform。

## 更长期方向

如果项目看板、自动开启对话和状态回写得到持续使用，再评估：

- 对话分叉、比较与人工合并；
- 多 Agent 调度；
- 更完整的 Coding Platform；
- 独立 Agent 产品或第三方运行时深度集成。
